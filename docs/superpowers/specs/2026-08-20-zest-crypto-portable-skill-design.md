# Zest Crypto Portable Skill Design

Date: 2026-08-20
Status: Direction approved; specification awaiting review
Target skill: `zest-crypto`

## 1. Decision

Build the first advanced-CTF extension as a portable Agent Skill named `zest-crypto`.

The skill will optimize for **time to a verified solve** on paper-backed, solver-heavy cryptography challenges. It will combine:

- a strict intake and fingerprint workflow;
- a small curated catalog of AttackCards with explicit preconditions and rejection rules;
- deterministic ranking helpers;
- reusable solver templates for the most common high-value attacks;
- paper and implementation retrieval guidance when the local catalog is insufficient;
- proof-oriented validation and case artifacts.

The skill will use the existing Zest CLI for byte normalization and triage when available, and installed specialist tools such as SageMath, Python, Z3, or `fpylll` when an attack requires them. It will not silently install tools, start services, or depend on a persistent server.

A later plugin may add managed runtimes, persistent caches, paper indexing, sandbox workers, and interactive tool APIs. Those concerns are deliberately outside this first portable package.

## 2. Problem

Hard crypto CTF challenges are rarely blocked by a missing Base64 decoder. The expensive part is usually one or more of the following:

1. recognizing the mathematical structure hidden behind challenge-specific names and code;
2. identifying the exact assumptions under which a known attack applies;
3. finding the relevant paper, section, or working implementation;
4. translating the challenge parameters into a reliable Sage/Python solver;
5. rejecting attractive but invalid hypotheses quickly;
6. proving that a recovered key, state, message, or flag is correct.

The current Zest skills are intentionally strong at deterministic byte transformations, light cryptography, and artifact triage. They hand off RSA, ECC, lattice, unknown-key recovery, and other math-heavy work. `zest-crypto` fills that boundary without turning the Zest core into an unbounded solver framework.

## 3. Goals

### 3.1 Primary goals

- Reduce time from challenge intake to the first mathematically justified attack hypothesis.
- Prefer cheap disproofs before expensive solver jobs.
- Make attack selection explainable through observed signals, met preconditions, rejection conditions, cost, and citations.
- Support paper-derived challenges with an offline-first, online-fallback research workflow.
- Produce a replayable solver and proof artifact rather than only a candidate flag.
- Remain installable as a normal portable Agent Skill from `SEORY0/zest-skill`.

### 3.2 Quality goals

- Deterministic ranking for the same fingerprint and AttackCard catalog.
- No claim of success without a verification step appropriate to the challenge.
- Clear reporting when an attack is blocked by missing evidence or tooling.
- Small core instructions with progressive disclosure into references, data, and templates.
- No automatic mutation of challenge inputs and no implicit network use.

## 4. Non-goals

The first version will not:

- claim to solve every cryptography challenge;
- bundle SageMath, Z3, `fpylll`, or other large runtimes;
- install system or language dependencies without explicit user authorization;
- run a persistent paper database, vector index, cache daemon, or MCP server;
- provide an unrestricted autonomous exploit sandbox;
- scrape or redistribute full papers;
- make heuristic plaintext or flag shape sufficient proof;
- replace Zest's existing byte-transform and CTF-triage skills;
- cover post-quantum cryptanalysis, general-purpose symbolic cryptanalysis, or every custom algebraic construction in v1.

## 5. Initial vertical

Version 1 targets **paper-backed, solver-heavy cryptography**, with two complementary tiers.

The baseline tier covers attacks that should be recognized and tested quickly before deeper research:

- RSA small-exponent and message-relation attacks;
- univariate small roots;
- repeated or partially exposed signature nonces;
- recoverable PRNG state;
- a representative adaptive crypto oracle.

The research tier proves that the skill can canonicalize recent challenge-specific wrappers to a paper family:

- matrix-product invariants followed by lattice search;
- fast correlation attacks that first require a low-weight polynomial multiple;
- ECDSA nonces generated by an LCG and recovered with lattice techniques;
- Wagner-style generalized birthday search;
- FROST-style threshold Schnorr protocol analysis;
- UOV hidden-structure attacks behind a wrapper construction;
- CSIDH/isogeny variants with auxiliary-point leakage.

These research-tier families are drawn from 2024-2025 challenge evidence and are intentionally stored under canonical family IDs rather than challenge titles. A challenge example is provenance for a card, not the card's identity.

Symmetric-mode misuse remains in scope for routing and validation, but v1 does not attempt broad key search. Encoding-only and known-parameter transforms continue to route to `zest-ctf` or `zest`.

## 6. User-visible contract

### 6.1 Trigger description

The front matter description must make the routing boundary explicit. The intended wording is:

> Analyze and solve CTF cryptography challenges with an evidence-driven workflow when the task involves RSA, ECC, lattices or small roots, PRNG state recovery, signatures, crypto oracles, or a paper-derived construction. Use Zest for byte normalization and installed Sage/Python/Z3 tools for solver work; route ordinary encoding-only blobs to zest-ctf.

### 6.2 Expected input

The skill accepts any combination of:

- a challenge statement;
- source code;
- public parameters or transcripts;
- local artifact paths;
- a remote challenge endpoint when the user has authorized interaction;
- constraints such as time, query budget, or available runtimes.

The skill must distinguish public CTF constants from real credentials. Challenge-provided public values may be recorded in the case workspace. Because the skill must work when installed alone, it carries these rules directly:

- public challenge constants may appear in solver source and commands when they are not credentials;
- contest tokens, session cookies, private endpoints, and real keys must not appear in argv, URLs, shell history, transcripts, manifests, or committed files;
- pass secrets through stdin, a process environment supplied at execution time, or a case-local file with restrictive permissions;
- redact secret-bearing command output before it becomes a case artifact;
- never upload sensitive artifacts to a hosted browser tool, paper-search service, or unrelated endpoint;
- do not commit recovered flags unless the repository explicitly contains public challenge solutions.

### 6.3 Expected output

For a completed solve, the agent reports:

- the winning attack and why its preconditions hold;
- the exact solver or replay command;
- the recovered value or flag;
- the validation performed;
- the paths to the case manifest, solver, transcript, and proof artifacts;
- citations used to derive the attack, when applicable.

For an incomplete solve, the agent reports:

- the strongest remaining hypotheses;
- which precondition or tool blocks each hypothesis;
- which cheap probes were already rejected;
- the next highest-information action.

## 8. Core workflow

The skill uses the following state machine:

```text
intake
  -> fingerprinted
  -> ranked
  -> probed
  -> attempted
  -> verified | rejected | blocked
```

### 8.1 Intake and case workspace

Create a fresh, case-specific directory outside the challenge source tree when possible. The directory name includes a timestamp and a short digest, not challenge secrets.

The workspace contains:

```text
case/
├── manifest.json
├── inputs/
├── notes/
├── solvers/
├── transcripts/
└── proof/
```

Rules:

- never overwrite the supplied challenge artifacts;
- hash each input before analysis;
- copy only the files needed for the solve, or record immutable source paths;
- record tool names and versions before solver execution;
- write generated solvers and outputs under the case directory;
- do not commit flags, private endpoints, session tokens, or real secrets.

### 8.2 Fingerprint

The fingerprint is a structured summary of observations, not a conclusion. It records:

- input digests and file types;
- integer constants and their bit lengths;
- algebraic relationships explicitly visible in code or transcripts;
- repeated values such as nonces, IVs, moduli, signatures, or outputs;
- primitive and library names;
- oracle access, query limits, response classes, and timing visibility;
- known plaintext, flag format, and controllable fields;
- installed solver tools and versions;
- links or citations embedded in the challenge.

`scripts/fingerprint.py` performs conservative extraction from text and source files and emits JSON. The agent must label inferred relationships separately from directly observed facts.

The v1 fingerprint shape is:

```json
{
  "schema_version": 1,
  "case_id": "example-4f2a91c0",
  "inputs": [
    {
      "id": "challenge.py",
      "path": "inputs/challenge.py",
      "sha256": "<64 lowercase hex characters>",
      "media_type": "text/x-python"
    }
  ],
  "facts": [
    {
      "id": "fact-001",
      "key": "rsa.public_exponent",
      "value": 3,
      "value_type": "integer",
      "status": "observed",
      "evidence": {
        "input_id": "challenge.py",
        "locator": "line 12"
      }
    }
  ],
  "capabilities": [
    {
      "command": "sage",
      "available": true,
      "version": "10.6"
    }
  ],
  "constraints": {
    "network": "disabled",
    "max_seconds": 300,
    "max_memory_mb": 4096,
    "max_oracle_queries": 0
  }
}
```

Schema rules:

- `case_id` is non-secret and derived from a label plus an input digest prefix.
- `path` is case-relative; source paths outside the case are recorded separately in local notes and are not published.
- `facts[].key` comes from the finite vocabulary documented in `attack-card-schema.md`.
- `value_type` is one of `boolean`, `integer`, `number`, `string`, `integer_list`, or `string_list`.
- `status` is one of `observed`, `derived`, or `inferred`.
- `observed` facts cite a direct input location; `derived` facts cite the source fact IDs and derivation; `inferred` facts state a rationale and may be used as signals but never satisfy a hard precondition by themselves.
- `constraints.network` is `disabled` or `allowed`; omission means `disabled`.
- missing facts remain missing. The extractor must not synthesize a default value that changes condition truth.

The minimum v1 fact-key vocabulary is fixed here; `attack-card-schema.md` may add keys only with a schema-version change:

| Key | Type | Meaning |
| --- | --- | --- |
| `rsa.modulus` | `integer` | one RSA modulus |
| `rsa.moduli` | `integer_list` | all observed RSA moduli |
| `rsa.public_exponent` | `integer` | one shared public exponent |
| `rsa.public_exponents` | `integer_list` | all observed public exponents |
| `rsa.ciphertexts` | `integer_list` | aligned RSA ciphertext samples |

| `rsa.message_relation_type` | `string` | normalized relation such as `affine` |
| `rsa.moduli_pairwise_coprime` | `boolean` | derived pairwise-gcd result |
| `rsa.exponents_coprime` | `boolean` | derived exponent-gcd result |
| `rsa.public_exponent_ratio` | `number` | `e / n` for the single-key case |
| `rsa.factorization_verified` | `boolean` | an exact factorization was checked against `n` |
| `rsa.private_exponent` | `integer` | a recovered private exponent retained as case evidence |
| `lattice.polynomial` | `string` | normalized polynomial expression |
| `lattice.modulus` | `integer` | modulus for the polynomial congruence |
| `lattice.unknown_bound` | `integer` | claimed upper bound on the unknown root |
| `signature.scheme` | `string` | normalized signature family |
| `signature.sample_count` | `integer` | number of aligned signature samples |

Use the Zest CLI, when installed, for deterministic preprocessing such as decoding, hashing, strings, entropy, file type detection, carving, and byte conversion. Do not ask Zest `magic` to stand in for mathematical attack selection.

### 8.3 Rank AttackCards

`scripts/rank_attack_cards.py` reads the fingerprint and the bundled catalog. Ranking follows this order:

1. reject cards whose exclusion rules match;
2. reject or mark blocked cards with unmet hard preconditions;
3. score matched positive signals;
4. prefer attacks with stronger evidence and cheaper probes;
5. apply an expected-cost penalty;
6. break ties deterministically by card identifier.

The output includes the score explanation. A numerical score never overrides an unmet hard precondition.

Conditions use a deliberately small JSON predicate language:

```json
{
  "fact": "rsa.public_exponent",
  "op": "eq",
  "value": 3
}
```

Supported operators are `exists`, `eq`, `neq`, `lt`, `lte`, `gt`, `gte`, `in`, `contains`, `len_eq`, and `len_gte`. Predicates may be combined with one top-level `all`, `any`, or `not`. Nested boolean groups deeper than two levels are rejected by the catalog validator.

Every predicate evaluates to `true`, `false`, or `unknown`:

- an absent fact produces `unknown` except for `exists`, which produces `false`;
- an `inferred` fact may satisfy a signal but produces `unknown` for `requires`, `rejects`, and `negative_matches`;
- a type mismatch is a catalog or fingerprint validation error, not `false`;
- all evaluation is local and deterministic.

Card state is computed before score. Each `negative_matches` entry has `id`, `when`, `reason`, and `unknown_policy`, where `unknown_policy` is `ignore` or `block`:

- any `rejects` predicate that is `true` makes the card `rejected`;
- any `negative_matches.when` predicate that is `true` makes the card `rejected`;
- any `requires` predicate that is `false` makes the card `rejected`;
- any `negative_matches.when` result of `unknown` with `unknown_policy: block` makes the card `blocked`;
- otherwise, any `requires` predicate that is `unknown` makes the card `blocked`;
- otherwise the card is `eligible`.

Only `eligible` cards enter the default top-three list. Blocked and rejected cards are returned separately with reasons so the agent can collect missing evidence or avoid repeated dead ends.

The ranker emits:

```json
{
  "schema_version": 1,
  "fingerprint_sha256": "<digest>",
  "catalog_sha256": "<digest>",
  "eligible": [
    {
      "card_id": "rsa.hastad.broadcast",
      "score": 75,
      "matched_signals": ["same-small-e", "enough-distinct-moduli"],
      "unmatched_signals": [],
      "evidence_fact_ids": ["fact-001", "fact-004"],
      "required_tools": ["python3"]
    }
  ],
  "blocked": [],
  "rejected": []
}
```

Scores are signed integers. Each matched signal contributes its declared integer weight from `-100` to `100`; the cost penalty is fixed by class (`low: 0`, `medium: 10`, `high: 25`, `oracle-bound: 15`) and is subtracted once. Sort by descending score and then ascending `card_id`.

The agent inspects the top three eligible cards by default. It may expand the list when fewer than three cards are eligible, a top card fails its probe or verification, or additional eligible cards are nearly tied with third place.

### 8.4 Run cheap probes

Before adapting a full solver, run attack-specific probes that can quickly falsify the hypothesis. Examples include:

- `gcd` across moduli and public values;
- continued-fraction convergence checks;
- modulus and unknown-bound comparisons;
- repeated or linearly related nonce detection;
- signature equation consistency;
- sample count checks for PRNG recovery;
- oracle response-class and noise checks;
- lattice determinant and expected-root bound sanity checks.

Independent, low-cost probes may run in parallel, with a default maximum of three. Expensive lattice reduction, brute force, or high-query oracle loops require a stated budget before execution.

### 8.5 Adapt and execute a solver

Copy the closest bundled template into `case/solvers/`, preserve its provenance, and adapt only the challenge-specific inputs and equations.

Before running:

- check the required tool with `command -v` or its platform equivalent;
- record the exact version;
- state expected time, memory, and oracle-query cost when meaningful;
- keep network disabled unless the challenge itself or paper retrieval requires it and the user has placed that endpoint in scope;
- use bounded timeouts for solver experiments;
- save stdout and stderr to the case workspace.

If the required runtime is missing, do not install it automatically. Report the missing capability and continue with any available probes or an equivalent installed tool.

### 8.6 Validate

A flag-shaped output is a candidate, not proof. Validation must use one or more of:

- recomputing the public equation with the recovered secret;
- re-encrypting, re-signing, or regenerating output;
- checking all supplied samples, not only the one that produced the flag;
- replaying the oracle transcript against a local harness or authorized endpoint;
- verifying a factorization or group relation exactly;
- demonstrating a reversible byte pipeline;
- comparing a derived key or state against independent challenge evidence.

Store the validation command and result under `case/proof/`. Mark a hypothesis `rejected` when proof fails and return to the next ranked card.

## 9. AttackCard model

Each AttackCard is a compact, versioned description of when and how to try one attack. The machine-readable catalog is authoritative for ranking; family documents carry longer mathematical explanations.

The catalog is a JSON array. Each entry conforms to this shape:

```json
{
  "schema_version": 1,
  "id": "rsa.wiener.small-d",
  "version": 1,
  "title": "Wiener attack on a small RSA private exponent",
  "canonical_family_id": "rsa.small-private-exponent",
  "family_aliases": ["small d", "continued fraction RSA"],
  "summary": "Recover d from convergents of e/n when d is sufficiently small.",
  "parameter_signature": ["rsa.modulus", "rsa.public_exponent"],
  "signals": [
    {
      "id": "large-public-exponent",
      "when": {"fact": "rsa.public_exponent_ratio", "op": "gt", "value": 0.5},
      "weight": 20,
      "reason": "A large e can be consistent with an unusually small d."
    }
  ],
  "requires": [
    {
      "id": "public-key-known",
      "when": {"all": [
        {"fact": "rsa.modulus", "op": "exists"},
        {"fact": "rsa.public_exponent", "op": "exists"}
      ]},
      "reason": "The continued-fraction attack needs n and e."
    }
  ],
  "rejects": [],
  "negative_matches": [],
  "cheap_probes": [
    {
      "id": "scan-convergents",
      "instruction": "Test convergents of e/n and keep only exact RSA factorizations.",
      "max_seconds": 10,
      "produces_facts": ["rsa.factorization_verified", "rsa.private_exponent"]
    }
  ],
  "expected_cost": {
    "class": "low",
    "notes": "Polynomial-time continued-fraction scan."
  },
  "tooling": [
    {
      "command": "python3",
      "required": true,
      "packages": [],
      "reason": "The bundled template uses standard-library integer arithmetic."
    }
  ],
  "template": "assets/solver-templates/rsa_wiener.py",
  "procedure": [
    {
      "id": "adapt-template",
      "instruction": "Copy the template into the case and supply n, e, and ciphertext."
    }
  ],
  "citations": [
    {
      "kind": "paper",
      "paper_id": "doi-or-canonical-id",
      "title": "Canonical source title",
      "url": "https://canonical.example/paper",
      "year": 1990,
      "section": "Theorem or algorithm used",
      "assumptions": ["The attack's exact mathematical assumptions, recorded as a concise paraphrase."],
      "verified_on": "2026-08-20"
    }
  ],
  "examples": [
    {
      "challenge_id": "event-year-slug",
      "event": "Official event name",
      "year": 2025,
      "repo_url": "https://github.com/owner/repo",
      "repo_sha": "40-character commit SHA",
      "source_path": "path/to/challenge-or-writeup",
      "source_lines": "L10-L40",
      "inference_level": "direct"
    }
  ],
  "verification": [
    {
      "kind": "equation",
      "instruction": "Verify p*q=n and e*d congruent to 1 modulo lcm(p-1,q-1), then decrypt and re-encrypt."
    }
  ]
}
```

Field rules:

- `canonical_family_id` is stable across challenge titles and wrapper variants.
- `family_aliases` and `parameter_signature` support retrieval but do not bypass conditions.
- `signals` are weighted observations that raise or lower rank.
- `requires` are hard conditions; each has a stable identifier and reason.
- `rejects` are conditions that make the card inapplicable.
- `negative_matches` name common false friends and the evidence that distinguishes them. A true predicate rejects the card; an unknown predicate follows its explicit `unknown_policy`.
- `cheap_probes` contain bounded tests, declared output facts, and no implicit dependency installation.
- `expected_cost` is one of `low`, `medium`, `high`, or `oracle-bound`, with notes.
- `tooling` lists commands and import packages. Package names are diagnostic only; the skill never runs an installer automatically.
- `template` is a package-relative path or `null`.
- `procedure` is an ordered, concise solver outline.
- `citations` identify an original or authoritative source, exact identifier, relevant section or algorithm, assumptions, and verification date.
- `examples` anchor family mapping to immutable challenge-source revisions. `inference_level` is `direct` when the source cites or names the construction, or `inferred` when the mapping is based on code and description.
- `verification` states how to prove the result for this attack family.

Before synthesizing a solver for a research-tier card, the agent must pass five gates:

1. **Source gate:** one pinned challenge source anchor and one exact paper identifier exist.
2. **Family gate:** aliases and variants map to one canonical family rather than a challenge title.
3. **Assumption gate:** challenge parameters satisfy the cited algorithm's assumptions; an inferred fact cannot pass this gate alone.
4. **Toy-instance gate:** a reduced invariant or faithful toy model behaves as predicted.
5. **Negative gate:** the card's named false-friend paths have been checked or explicitly ruled out.

## 10. Paper and implementation retrieval

### 10.1 Offline-first behavior

The bundled catalog is queried first. This keeps common attacks fast, deterministic, and usable without network access.

Each citation stores:

- title and authors;
- venue or archive and year;
- canonical URL or DOI;
- the relevant theorem, section, or algorithm;
- the assumptions used by the AttackCard;
- an implementation URL and revision when one is relied on;
- the date the metadata was verified.

Full papers are not bundled unless their license and size make that explicitly appropriate. The skill normally stores metadata and a concise original summary.

### 10.2 Online fallback trigger

Research online only when at least one of the following holds and network use is permitted:

- no local card matches the observed primitive or construction;
- all top-ranked cards fail a hard precondition;
- challenge code cites an unfamiliar construction or paper;
- the attack depends on a variant not covered by the local assumptions;
- a local card lacks a trustworthy implementation path.

Search queries combine the primitive, the abnormal relationship, and attack-oriented terms. Prefer primary sources in this order:

1. IACR ePrint, proceedings, or an author-hosted paper;
2. official documentation or an author-maintained implementation;
3. official CTF challenge archives and author writeups;
4. secondary writeups only for navigation or independent implementation hints.

Semantic Scholar and Crossref may be used to discover metadata, but a discovery index is not treated as the mathematical authority. The agent must verify the original source and identify the exact assumptions before applying an attack.

### 10.3 Research result

Online research writes a case-local literature note containing:

- the query and access date;
- canonical links;
- relevant sections and assumptions in the agent's own words;
- the mapping from paper variables to challenge variables;
- implementation provenance;
- unresolved gaps.

Portable v1 does not mutate the bundled catalog automatically. A useful case-local card can be proposed later through a reviewed repository change.

## 11. Runtime and permission model

The portable skill coordinates tools already present in the environment.

### 11.1 Preferred tools

- `zest`: byte normalization, decoding, hashing, entropy, strings, file typing, and carving;
- Python 3 standard library: parsing, integer arithmetic, transcripts, and lightweight solvers;
- SageMath: polynomial rings, small roots, finite fields, elliptic curves, and lattices;
- Z3: bounded bit-vector or constraint formulations where appropriate;
- `fpylll`: optional lower-level lattice work;
- PyCryptodome: optional primitive validation and challenge-compatible conversions.

The skill must inspect availability and version before choosing a path. It may write a solver that declares a missing dependency, but it must not claim that solver was executed.

### 11.2 Network boundaries

- Paper lookup is optional and explicit in the case record.
- Remote oracle access is allowed only for the challenge endpoint placed in scope by the user.
- Query limits and concurrency must respect contest rules and challenge stability.
- Real-world targets, unrelated infrastructure, and credential testing are outside scope.
- A local replay harness is preferred once enough oracle behavior has been captured.

### 11.3 Resource boundaries

The skill records a budget before high-cost work. The default strategy is:

- up to three concurrent cheap probes;
- one expensive solver attempt at a time unless resource limits are known;
- bounded execution time and captured logs;
- explicit checkpointing for long lattice or oracle work;
- no endless brute force presented as a strategy.

## 12. Relationship to existing Zest skills

The routing boundary is:

| Task | Skill |
| --- | --- |
| Unknown blob, encoding chain, compression, XOR, ROT, known-parameter symmetric crypto | `zest-ctf` |
| General deterministic data transformation | `zest` |
| File carving and lightweight artifact triage | `zest-triage` |
| RSA, ECC, lattices, signatures, PRNG state, mathematical key recovery, crypto oracles, paper-derived constructions | `zest-crypto` |

`zest-crypto` may call Zest operations during intake, but it does not duplicate the generated operation catalog. Its package must remain independently understandable when installed alone: it explains the minimal Zest command role and degrades clearly when the CLI is absent.

## 13. Failure handling

The skill treats the following as normal outcomes:

- **Rejected:** a cheap probe or exact equation disproves the attack.
- **Blocked by evidence:** a required relation, sample, transcript, or bound is absent.
- **Blocked by tooling:** the necessary runtime is not installed.
- **Blocked by budget:** expected time, memory, or query cost exceeds the stated limit.
- **Unsupported construction:** the local catalog has no precise card and online research did not establish one.
- **Unverified candidate:** a plausible value exists but proof failed or cannot be performed.

The agent must not collapse these into “could not solve.” Each outcome preserves the evidence needed for the next attempt.

## 14. Testing and evaluation

### 14.1 Static validation

- Run the `quick_validate.py` supplied by the installed `skill-creator` authoring package on `skills/zest-crypto`; this is an authoring cross-check, not a runtime dependency of the published skill.
- Extend and run the repo-local `node --test scripts/skill-package.test.mjs` checks so validation remains startable without the authoring package.
- Validate `attack-cards.json` with `scripts/validate_attack_cards.py`.
- Verify every relative Markdown link remains inside the standalone skill package.
- Verify every solver template referenced by a card exists.
- Verify citation records contain a canonical URL and relevant section or algorithm.
- Verify the publication dry run includes every `zest-crypto` file.
- Verify helper scripts use the Python standard library and contain no network client, package-installer, daemon, or service-starting path.
- Verify the default fingerprint constraint is `network: disabled` when the field is absent.
- Verify every file created by a helper stays under an explicitly supplied, fresh case directory.

### 14.2 Deterministic helper tests

Add repository tests for:

- conservative fingerprint extraction from representative Python, Sage, and transcript inputs;
- rejection of malformed or ambiguous AttackCards;
- hard-precondition gating;
- stable ranking and tie breaking;
- score explanations;
- missing-tool reporting;
- preservation of input files and fresh output paths.

### 14.3 Forward evaluation

An independent agent receives challenges without the intended AttackCard label. Evaluation records:

- top-1 and top-3 card hit rate;
- time to first justified hypothesis;
- time to verified proof;
- false-positive and rejected-hypothesis counts;
- deterministic rerun behavior;
- whether missing evidence or tools were reported accurately.

The initial evaluation set contains eight blind manifests:

- six have one precise intended AttackCard label;
- two are intentionally ambiguous and have only an intended canonical-family label;
- at least three are runnable end to end;
- at least two come from official archived CTF challenges;
- at least one requires a cited paper or paper-derived technique.

Synthetic fixtures may cover edge cases, but they cannot be the entire evaluation set. A challenge title and intended card ID are hidden from the solving agent until scoring.

### 14.4 Manual QA gate

Install the skill from a clean local package copy and exercise it as a user would:

1. route an encoding-only case away from `zest-crypto`;
2. complete an offline case while network access is unavailable;
3. rank a supported mathematical crypto case;
4. adapt and execute a bundled solver template;
5. validate the recovered result;
6. exercise a missing-tool path and confirm no installer command is attempted;
7. exercise an offline no-match path and confirm no network lookup occurs;
8. allow paper research for a test case only after its case constraint is set to `network: allowed`;
9. confirm no daemon, persistent cache, or service artifact is created;
10. confirm challenge inputs remain unchanged and every generated file stays inside the fresh case directory.

## 15. Acceptance criteria for v1

Version 1 is complete when all of the following are true:

- `zest-crypto` installs as a standalone portable skill.
- Its trigger description distinguishes math-heavy crypto from encoding-only CTF work.
- The core loop produces a case manifest, ranked cards, solver artifact, and proof record.
- The catalog contains 21 precise, validated AttackCards across the baseline families and paper-derived construction tier.
- Six bundled solver templates execute on their corresponding fixtures.
- Ranking is deterministic and explains every top-three result.
- An unmet hard precondition cannot be overridden by heuristic score.
- Every successful fixture has an exact mathematical or replay proof.
- Blind forward evaluation meets these initial gates:
  - the exact intended AttackCard appears in the top three for all six precisely labeled manifests;
  - the exact intended AttackCard ranks first for at least four of those six manifests;
  - the intended canonical family appears in the top three for both intentionally ambiguous manifests;
  - all three runnable fixtures are solved and verified;
  - zero candidates are labeled solved on flag shape alone;
  - reruns produce the same top-three order for unchanged inputs and catalog.
- Current-year evaluation requires the exact intended AttackCard in the top three for
  all five pinned 2026 cases: `subset-sum-query-schedule`, `lfstream`,
  `slide-periodic-round`, `goldwasser-micali-replication`, and `rotor-cipher`.
  The `lfstream` and `Rotor Cipher` cases must also complete end-to-end proof.
- Offline mode performs no paper lookup, remote request, install attempt, or persistent-service startup.
- Online paper research occurs only when `constraints.network` is `allowed` and records the permission state and sources in the case.
- Missing specialist tools produce a blocked result without attempting to install software.
- Helper outputs remain confined to a fresh case directory, and all challenge inputs retain their original digest.
- The existing Zest build and test suite remains green.
- `npm run publish:skill -- --dry-run` shows the complete portable package without pushing.

These gates validate a useful first vertical, not universal hard-crypto coverage. Failures from later real CTF use become evidence for new cards, templates, or a plugin capability.

## 16. Delivery sequence

Implementation should be split into reviewable stages:

1. **Skill shell and contracts**
   - `SKILL.md`, workflow, validation rules, case schema, packaging tests.

2. **AttackCard system**
   - schema, validator, deterministic ranker, fixtures, initial catalog.

3. **Solver templates**
   - six templates, exact validation, tool/version checks.

4. **Literature workflow**
   - citation metadata, source hierarchy, paper-to-challenge variable mapping.

5. **Forward evaluation and refinement**
   - blind cases, timing and ranking metrics, corrections based on observed failures.

6. **Publication**
   - full validation, dry-run mirror, then a separately authorized push of the source and standalone skill repositories.

## 17. Future plugin boundary

Promote capabilities into a plugin only when repeated use shows that portability alone is the bottleneck. Candidate plugin services are:

- a managed Sage/Z3/`fpylll` runtime;
- content-addressed challenge and solver cache;
- searchable paper and AttackCard index;
- sandboxed long-running solver workers;
- oracle transcript capture and replay tools;
- benchmark and telemetry storage;
- an MCP surface for fingerprints, ranked attacks, evidence, and proofs.

The portable skill remains the policy and reasoning layer. The plugin would supply durable execution and retrieval services without changing the skill's proof requirements.

## 18. Evidence informing the design

- The existing Zest repository models deterministic byte-in/byte-out operations and bounded `magic` search, which makes it appropriate for preprocessing rather than unbounded mathematical solving.
- Anthropic's report on frontier models in 2025 cyber competitions highlights tooling, parallelization, and long-horizon state management as material constraints; their evaluated agent solved none of the PlaidCTF or DEF CON Qualifier challenges in that setup: [Claude is competitive with humans in (some) cyber competitions](https://www.anthropic.com/research/cyber-competitions).
- The official Google CTF 2024 McEliece solver demonstrates a recent challenge that directly operationalizes research-grade structural cryptanalysis in Sage: [Google CTF 2024 McEliece solver](https://github.com/google/google-ctf/blob/main/2024/quals/crypto-mceliece/challenge/solve.sage).
- Recent author-maintained challenge archives show why canonical paper families must be separated from challenge titles: [HITCON CTF 2024 MatProd](https://github.com/maple3142/My-CTF-Challenges/blob/7b3e786a2c20812f4da23536c7817bdfe8113dd6/HITCON%20CTF%202024/MatProd/README.md), [HITCON CTF 2024 Hyper512](https://github.com/maple3142/My-CTF-Challenges/blob/7b3e786a2c20812f4da23536c7817bdfe8113dd6/HITCON%20CTF%202024/Hyper512/README.md), and [SekaiCTF 2025 law-and-order](https://github.com/project-sekai-ctf/sekaictf-2025/blob/683dd81ae520581add40ec21c4819866e28cbde4/crypto/law-and-order/challenge/app/chall.py).
- The research-tier cards are anchored to primary families including [matrix-product cryptosystem blueprints](https://eprint.iacr.org/2023/1745), [low-weight polynomial multiples](https://eprint.iacr.org/2007/423), [Wagner's generalized birthday problem](https://link.springer.com/chapter/10.1007/3-540-45708-9_19), [FROST](https://eprint.iacr.org/2020/852), and [CSIDH](https://eprint.iacr.org/2018/383).
- Official challenge archives provide reproducible evaluation material: [Google CTF 2025 qualifiers](https://github.com/google/google-ctf/tree/main/2025/quals) and [DEF CON CTF 2025 qualifiers](https://github.com/Nautilus-Institute/quals-2025).
- Paper metadata discovery can use [Semantic Scholar's Academic Graph API](https://api.semanticscholar.org/api-docs/) and the [Crossref REST API](https://support.crossref.org/hc/en-us/articles/214320426-REST-API), while mathematical claims remain anchored to primary papers and proceedings.

## 19. Resolved design choices

- **Portable skill first:** chosen by the project owner.
- **Hybrid research:** curated offline cards first, online primary-source retrieval only on a defined miss.
- **Focused initial domain:** paper-backed public-key and solver-heavy crypto, not all CTF categories.
- **Time-to-proof metric:** optimize for a verified result, not the number of attempted operations.
- **External tools allowed:** use installed tools after capability and version checks; never install silently.
- **Proof required:** no solve claim based solely on printable text or flag format.
- **No persistent service in v1:** caches, managed runtimes, and MCP tooling remain plugin work.
- **Source-of-truth repository:** implement under `SEORY0/zest`, then mirror through the existing publisher.
